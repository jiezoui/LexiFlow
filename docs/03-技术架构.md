# LexiFlow 技术架构文档

> **TL;DR 1**：Java 21 + Spring Boot 3.3 的**模块化单体**，10 个业务模块共享一个进程、一个 MySQL 8.4，模块间只走 `api` 包接口 + DTO，用 ArchUnit 把边界钉死，将来要拆微服务时按模块切即可。
> **TL;DR 2**：产品两条主线（词书背单词 / 语境采词）在架构上**共用一个 FSRS 引擎、一张 `user_word` 表、一个 `due_at`**（见 §5.1）；词书进度是派生视图，不是第二套计数器。
> **TL;DR 3**：AI 分两层——**机翻层系统预置零配置可用**（腾讯/微软/Google/DeepL + 自建 LibreTranslate 兜底，按 region 双降级链），**LLM 层 BYOK**（用户自带 Key，AES-GCM 加密入库）；统一走 `AiRouter` + `capability` 路由，失败自动降级（见 §5.3）。
> **TL;DR 4**：刻意不引入 Elasticsearch（MySQL FULLTEXT + ngram 够用）和 RabbitMQ（`async_job` 表状态机 + `@Scheduled` 轮询够用）；词典查询走本地 ECDICT + Redis，P99 < 20ms，AI 只做增值层。

### 1.1 技术选型与理由

| 层 | 选型 | 为什么 |
|---|---|---|
| 语言/框架 | Java 21 + Spring Boot 3.3 | 虚拟线程（Loom）让"高 IO 等待 + 低 CPU"的 AI 调用不用写 reactive 也能撑住并发；虚拟线程直接配 `spring.threads.virtual.enabled=true` |
| ORM | MyBatis-Plus | 词典/统计类查询大量手写 SQL 和批量导入（ECDICT 770 万行），JPA 的抽象在这里是负担；MP 的 `BaseMapper` 又省掉 CRUD 样板 |
| 安全 | Spring Security + JWT | 无状态 access token 便于将来水平扩容；refresh 放 Redis 才能主动吊销 |
| AI | Spring AI | 统一 `ChatClient` / `EmbeddingModel` 抽象，OpenAI 兼容端点只换 base-url；但**不直接暴露给业务**，外面再包一层 `AiRouter`（见 §5.3） |
| DB | MySQL 8.4 InnoDB / utf8mb4_0900_ai_ci | 8.0+ 才有可用的 `ngram` 全文索引和 JSON 函数；`_0900_ai_ci` 排序规则性能优于 `utf8mb4_general_ci` 且大小写/重音不敏感，正好匹配词典查询 |
| 缓存 | Redis 7 | 四类用途：① 词典热词 ② JWT refresh / 黑名单 ③ AI 结果二级缓存（一级在 `ai_cache` 表）④ 令牌桶限流 |
| 前端 | Vue 3 + TS + Vite + Pinia + Vue Router + Tailwind | Composition API 对播放器这种"强状态 + 高频更新"场景比 Options API 好组织；Vite 冷启动快，单人开发迭代体验优先 |
| 部署 | Docker Compose (mysql/redis/backend/nginx) | 单机四容器，一条 `docker compose up -d`；不上 K8s，单人项目运维预算为零 |
| 对象存储 | `StorageProvider` 接口 | 默认 LocalDiskStorage 零依赖起步，需要时切 MinIO / 阿里云 OSS，业务代码不动 |

**UI 组件库建议：选 shadcn-vue。** 理由：① 组件代码复制进仓库，样式完全可改，播放器字幕层、复习卡片这些强定制 UI 不会被组件库的样式打架；② 和 Tailwind 同一套设计 token，不会出现 Tailwind + Naive UI 双套间距/圆角体系；③ 按需复制，不引入整包体积。**代价**：需要自己维护复制进来的组件代码，升级不自动；表格、树、日期选择器这类重组件 shadcn-vue 成熟度不如 Naive UI，若后续要做复杂数据表格，可局部引入 Naive UI 的 `NDataTable` 单点补齐。

## 2. 架构风格：模块化单体（Modular Monolith）

### 2.1 为什么不一开始就微服务

| 维度 | 微服务的代价（在本项目） |
|---|---|
| 人力 | 单人开发。10 个服务 = 10 套构建/发布/配置/日志/监控，边际收益为负 |
| 运维 | 单机 Docker Compose 就能跑完的东西，微服务要加注册中心、配置中心、网关、链路追踪 |
| 事务 | `practice` 提交一次打字成绩要同时写 `practice_attempt` + 触发 `review` 的 FSRS 调度更新。单体里一个 `@Transactional` 搞定；微服务里这是 Saga + 补偿 + 幂等表 |
| 性能 | 模块间调用是 JVM 内方法调用（纳秒级），拆开变成网络往返（毫秒级）。学习类应用的一次页面加载会横跨 4~5 个模块 |
| 领域边界 | 项目还在演进期，模块边界会变。在代码里挪一个包 vs 在服务间挪一张表，成本差两个数量级 |
| **结论** | 拿"模块化单体"吃掉微服务的**边界收益**，同时不付它的**分布式代价** |

### 2.2 如何保证"将来拆得动"

四条硬规则，违反即测试失败（CI 拦住）：

1. **模块间只通过各模块 `api` 包里的接口 + DTO 通信。** `api` 包只允许出现接口定义、DTO record、枚举，不允许出现 Entity、Mapper、Service 实现。
2. **禁止跨模块直接注入别人的 Mapper / Repository。** 任何 `@Autowired XxxMapper` 只能出现在同模块 `internal` 内。
3. **模块内 `internal` 包对外不可见**，由 ArchUnit 强制。
4. **每个模块拥有自己的表，跨模块不做数据库 JOIN。** 需要聚合展示的场景用 read model / 预聚合表（`daily_stat`）。这条是最关键的一条——只要没有跨模块 JOIN，拆服务时数据库就能直接按模块切开。

### 2.3 ArchUnit 规则示例

```java
@AnalyzeClasses(packages = "com.lexiflow", importOptions = DoNotIncludeTests.class)
class ArchitectureTest {

    // 规则1：internal 包只能被本模块访问
    @ArchTest
    static final ArchRule internal_is_module_private = SlicesRuleDefinition
            .slices().matching("com.lexiflow.modules.(*)..")
            .namingSlices("module $1")
            .should().notDependOnEachOther()
            .ignoreDependency(  // 白名单：只允许依赖别人的 api 包
                    resideInAnyPackage("com.lexiflow.modules.."),
                    resideInAPackage("com.lexiflow.modules..api.."));

    // 规则2：Mapper 只能被同模块的 internal 使用
    @ArchTest
    static final ArchRule mapper_not_leaked = classes()
            .that().haveSimpleNameEndingWith("Mapper")
            .should().onlyBeAccessed().byClassesThat()
            .resideInAPackage("..internal..");

    // 规则3：api 包不得出现 Entity / Mapper（api 只有接口 + record DTO + enum）
    @ArchTest
    static final ArchRule api_is_clean = noClasses()
            .that().resideInAPackage("..modules..api..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..internal.entity..", "..internal.mapper..");

    // 规则4：ai 模块不得依赖任何业务模块
    @ArchTest
    static final ArchRule ai_is_infrastructure = noClasses()
            .that().resideInAPackage("com.lexiflow.modules.ai..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("com.lexiflow.modules.(user|wordbook|vocabulary|review|practice|media|reading|stats)..");

    // 规则5：无环依赖；规则6：controller 不得直接碰 Mapper
    @ArchTest
    static final ArchRule no_cycles = SlicesRuleDefinition
            .slices().matching("com.lexiflow.modules.(*)..").should().beFreeOfCycles();

    @ArchTest
    static final ArchRule controller_via_service = noClasses()
            .that().haveSimpleNameEndingWith("Controller")
            .should().dependOnClassesThat().haveSimpleNameEndingWith("Mapper");
}
```

```

           practice ──────► review, media, dictionary      user  独立无依赖
 L2 内容   media ─────────► ai, dictionary
           reading ───────► ai, dictionary
           review ────────► vocabulary, dictionary
           vocabulary ────► dictionary
 L1 基础   ai               不依赖任何业务模块
           dictionary       叶子，不依赖任何业务模块
 L0        infra ─► common  所有模块均可依赖

```

**依赖方向规约**

| 规则 | 说明 |
|---|---|
| `wordbook → dictionary + vocabulary + review + media` | 切词书与 headword 归一走 dictionary（读 `tag`/`frq`/`bnc`）；词进入学习即写 `user_word`（走 `VocabularyApi`，`source=WORDBOOK`）；进度与遗忘率读 review 的 FSRS 状态；例句从 media 的 `subtitle_cue` 捞（见 §5.2） |
| `practice → review + media + dictionary` | 练习产生 rating 交给 review 调度；句子素材来自 media；拼写校验用 dictionary |
| `media → ai + dictionary` | 字幕翻译走 ai；cue 分词走 dictionary |
| `reading → ai + dictionary` | 文章解析/翻译走 ai；分词与难度走 dictionary |
| `vocabulary → dictionary` | 生词入库前先 lemma 归一 |
| `review → vocabulary + dictionary` | 卡片背后的词义来自 vocabulary；FSRS 状态列（`state`/`due_at`/`stability`/`difficulty`）内联在 `user_word` 上，review 算完新状态后调 `VocabularyApi.applySchedule()` 回写——**表只由拥有者写**，review 不直接碰 `user_word` 的 Mapper |
| `stats → *` | **单向只读**，只调其他模块 api 的查询方法，禁止写；且没有任何模块可以依赖 stats |
| `ai → 无` | ai 是基础能力，不认识"生词本""字幕"这些概念，入参出参都是纯 AI DTO |
| **禁止环依赖** | ArchUnit `beFreeOfCycles()` 强制。若出现"A 需要 B、B 又需要 A"，一律改为事件/回调或把公共部分下沉到 dictionary/infra |
| **实现约定** | 跨模块调用一律注入 `XxxApi` 接口，Spring 装配到同进程内该模块 `internal` 的实现类。将来拆服务时，把 `XxxApi` 换成 Feign/HTTP client 即可，调用方零改动 |

## 4. 分层规范

```
controller  →  service  →  mapper
   VO       ←    DTO     ←   Entity
```

| 层 | 允许做 | 禁止做 |
|---|---|---|
| controller | 参数校验（`@Valid`）、DTO↔VO 转换、`Result` 包装、权限注解 | 任何业务判断、`if` 分支决定业务走向、直接注入 Mapper、开启事务 |
| service | 业务编排、**事务边界（`@Transactional` 只在这一层）**、调用其他模块 api、缓存读写 | 感知 HTTP（`HttpServletRequest`/`ResponseEntity`）、返回 Entity 给上层 |
| mapper | SQL、批量操作 | 业务逻辑、跨模块表 JOIN |

**三层模型不混用**（Entity **绝不**越过 service 边界；`api/dto` 里的 DTO 必须是 `record` 且不引用任何 Entity 类型）

| 类型 | 位置 | 用途 | 命名 |
|---|---|---|---|
| Entity | `internal/entity` | 与表一对一，字段名对齐列名 | `UserWord` |
| DTO | `api/dto`（对外）/ `internal/dto`（内部） | 模块间传输、service 入参出参 | `UserWordDTO` / `AddVocabCmd` |
| VO | `internal/vo` | 前端视图专用，可含拼装字段 | `UserWordVO` |

## 5. 关键设计决策

### 5.1 两条主线共用一个 FSRS 引擎

**决策**：词书背单词和视频/文章划词是两个**入口**，不是两套系统。

- 词书里的词一旦被用户选择"学"，就是 `user_word` 表里的**一行**，`source='WORDBOOK'`、`wordbook_id=X`；视频划词的行是 `source='VIDEO'`、`wordbook_id=NULL`。二者在复习队列里**完全平等，混合排期**，不做任何分组或加权。
- **只有一个 `due_at`，只有一个"今日复习"入口。** `wordbook` 模块**不允许**维护第二套进度计数器（不建 `learned_count` 之类的自增列）。
- 词书进度是**派生视图**，不是状态：

```
词书进度 = count(user_word WHERE user_id=U AND wordbook_id=X AND state>=REVIEW)
           ────────────────────────────────────────────────────────────────
                            wordbook.word_count

今日队列 = SELECT * FROM user_word WHERE user_id=U AND due_at<=NOW(3)
           ORDER BY due_at            ← 不 filter source，不 filter wordbook_id
```

| | |
|---|---|
| **理由** | 两套进度必然发散："CET6 词书 80%" 和"生词本 200 词"互不相干时，用户不知道自己到底会多少词，两个数字都会被怀疑。派生视图在定义上不可能和事实数据不一致。用户也不该被迫在"背词书"和"复习生词"之间做选择——今天要复习的就是今天要复习的，来源无关 |
| **代价** | 查词书进度要按 `wordbook_id` 聚合 `user_word`，比读一个计数器贵——必须建 `idx_user_wordbook_state (user_id, wordbook_id, state)` 覆盖索引；进度数字可做短 TTL（60s）Redis 缓存，但**缓存里存的仍是算出来的值**。`user_word` 一张表承载两类来源，字段必须能容纳两者：`source VARCHAR(20)` + **可空** `wordbook_id`，且校验规则是"`source=WORDBOOK` ⇔ `wordbook_id NOT NULL`"（service 层保证） |
| **替代方案** | ① 词书独立进度表 → 两套数据必然不一致，且用户看不到自己真实的总词汇量，等于把产品最核心的差异化拆掉；② 词书词不入 `user_word`，只在词书表里带状态 → 视频里遇到该词时无法识别"这是你正在背的词"，§5.2 的反向链路直接失效 |

### 5.2 例句供给链：`word_example` 全局例句池

**决策**：`word_example`（`lemma / source_type / text / translation / media_item_id / cue_id / start_ms / end_ms / quality_score / is_public`）是所有例句的唯一出口。`WordbookApi.examplesFor(userId, lemma)` 按以下优先级取：

```
1  用户自己看过的视频里含该 lemma 的 subtitle_cue   ← 有原声 + 情绪锚点，最强
2  公共例句池（其他用户视频挖掘，is_public=1）        ← 有原声，不属于你
3  词典自带例句（ECDICT / 导入词书的 example 列）      ← 无原声
4  AI 生成（capability=CHAT）                        ← 必须在 UI 标注"AI 生成"
```

**从 `subtitle_cue` 挖掘例句的规则**：① 句长 5–20 词（太短没语境，太长做卡面读不完）；② 该 cue 的 `tokens` lemma 集合包含目标词（复用 §5.9 的预分词结果，不重新分词）；③ 过滤过于生僻的上下文——cue 内除目标词外的词若有 >2 个 `frq` 排名在 20000 名以外，丢弃（例句不该比被解释的词更难）；④ `quality_score` 排序（词长适中度 + 上下文常见度 + 是否有官方译文 + 是否有清晰句界），取 top-N。

**挖掘是离线异步任务**：`job_type=MINE_EXAMPLES`，走 `async_job`（见 §5.8），在字幕解析完成后触发，**绝不在请求路径上做**——一集视频 800 条 cue × 每条十几个 lemma，实时算必然超时。

**反向链路（视频里标出"这句话里有你正在背的词"）**：后端提供 `WordbookApi.learningLemmaSet(userId)`（当前 `state<REVIEW` 或 due 在近期的 lemma 集合，几百到几千个），前端**一次性拿到**存进 `study` store，字幕渲染时与 `subtitle_cue.tokens` 的 lemma 集合求交——和 §5.9 的生词高亮是同一个 `Set` 求交，只是换一个集合、换一种着色。

| | |
|---|---|
| **理由** | 例句是词书体验的核心，而我们没有编辑团队；唯一能打的牌就是"这句话你听过"。做成全局池 + 优先级链，让"用户自己的语料"和"公共语料"用同一套读取接口，缺料时自动往下退，不会出现空白例句区。反向链路是产品差异化里价值最高的一条，而它的实现成本因为 `tokens` 已落库而近乎为零 |
| **代价** | `word_example` 会长得很大（每个 lemma 保留 top-N，需要定期裁剪 job）；挖掘有延迟，刚导入的视频不会立刻出现在例句里（UI 要能接受"暂无你的语料"状态）；公共池涉及"把 A 的字幕片段给 B 看"，只放**单句**且需 `is_public` 显式开关，自导入词书与私有素材默认不进池（见 01-product §9.2） |
| **替代方案** | ① 每次请求实时扫 `subtitle_cue` → 慢且重复计算确定性结果；② 只用 AI 生成例句 → 丢掉全部差异化，且质量不可控；③ 采购/抓取第三方例句库 → 版权不干净，明确列为 Non-goal |

### 5.3 AI 分两层：机翻层系统预置，LLM 层 BYOK

**决策**：`Capability` 枚举 `CHAT / TRANSLATE / ASR / TTS / PRONUNCIATION / EMBEDDING` 不变，但 `TRANSLATE` 与 `CHAT` 在**配置与计费模型上完全不同**，必须分层看。

**分工原则一句话：机翻负责"量"（整轨字幕、段落翻译），LLM 负责"质"（点词时的语境化释义）。**

#### 5.3.1 机翻层（`TRANSLATE`，系统预置，零配置可用）

**这是产品红线：新用户不填任何 key，必须能看到双语字幕。** 因此机翻 provider 的 key 由**部署者**配置在服务端环境变量里，不属于任何用户的 `ai_provider_config`。

| Provider | 免费额度 | 备注 |
|---|---|---|
| 腾讯 TMT | 500 万字符/月 | 国内首选，延迟最低 |
| 有道 | 有免费额度 | 国内备选 |
| 微软 Azure Translator | F0 层 200 万字符/月 | 国内外都通，全局主力 |
| Google Cloud Translation | 50 万字符/月 | 仅 GLOBAL 链 |
| DeepL Free | 50 万字符/月 | 质量最好，额度最小 |
| **自建 LibreTranslate** | **完全免费无限** | 随 Docker Compose 一起起，**最终兜底** |

```
region=CN      腾讯TMT ──► 有道 ──► 微软 ──► LibreTranslate
region=GLOBAL  微软 ──► Google ──► DeepL ──► LibreTranslate
                                              ↑ 永远在链尾，保证红线不破
```

- **免费额度用量计数**：`ai_usage_log` 之外另维护 `translate_quota(provider, period_ym, chars_used, chars_limit)`，Redis 计数器实时累加 + 落库对账，**按月重置**；某 provider 当月耗尽 → 路由直接跳过它降到下一环（不等它返回 429 才发现）。
- 字幕整轨翻译按 cue 批量打包送译（一次 20~50 条，减少往返），失败的批次单独重试而非整轨重来。

#### 5.3.2 LLM 精翻层（`TRANSLATE` / `CHAT`，BYOK）

- 用途：语境化释义、单句精翻、长难句解析、助记法、出题。LLM 做翻译时走 `TRANSLATE` capability，做对话或解释时走 `CHAT` capability；两者可以使用同一个 Provider，但必须分别配置、计量和降级。
- `OpenAiCompatibleProvider` 一个类覆盖 DeepSeek / Kimi / 通义千问 / Ollama / vLLM / OpenAI 本体——都兼容 OpenAI Chat Completions 协议，差异只在 `baseUrl` + `model` + 少量参数。
- **API Key 安全**：AES-GCM 加密入库（每条记录独立随机 12 字节 IV，存 `iv || ciphertext || tag`），主密钥 `LEXIFLOW_MASTER_KEY` 从环境变量读，**绝不入 git**；任何返回给前端的路径一律掩码为 `sk-***abcd`（保留前缀 + 末 4 位），掩码在 VO 转换器里做，不依赖前端。
- 未配置任何 LLM key 时，`CHAT` / LLM `TRANSLATE` 相关功能在 UI 上显示为"需要配置模型"，**但不影响任何主路径**（查词、默认机翻字幕、复习照常）。

#### 5.3.3 LLM 翻译不依赖微调

**决策**：第一版不建设微调训练平台，也不把任何微调模型作为运行依赖。翻译质量通过请求上下文、术语表、Prompt 版本和用户反馈闭环提升。

一次 LLM 翻译请求的输入至少包含：

```text
source_language / target_language
当前句子或段落
前后文（可选，按 token 预算截断）
来源标题、文章主题或视频信息
用户术语表与固定译法
翻译风格（学习者友好 / 直译 / 口语 / 技术文档）
prompt_version
```

统一请求 DTO：

```java
public record TranslationRequest(
        String sourceLanguage,
        String targetLanguage,
        String text,
        String contextBefore,
        String contextAfter,
        String sourceTitle,
        List<GlossaryTerm> glossary,
        String style,
        String promptVersion
) implements AiRequest<TranslationResult> {}
```

结果必须带 `aiGenerated = true`，并保存 `providerId`、`model`、`promptVersion`、`inputHash`，便于缓存、复现和比较不同模型。

缓存键至少包含：

```text
sha256(capability + model + promptVersion + normalizedInput + glossaryVersion)
```

用户对译文的修改不直接覆盖原结果，而是写入 `ai_feedback`：原文、AI 译文、用户修订译文、来源上下文、Provider、模型、Prompt 版本、评分和创建时间。后续优先用于 Prompt/术语表/路由评估；只有评测证明这些手段仍不足时，才考虑生成微调数据集。

**不要用微调承载动态知识**：视频字幕、BBC 文章、LessWrong 文章和用户当前阅读内容都必须通过上下文传入或检索得到，不写进模型权重。这样既能保持内容更新，也能让用户更换 Provider。

#### 5.3.4 Provider 与 capability 路由

`AiRouter` 的候选选择顺序：用户对该 capability 的配置 → 系统预置链 → 最终兜底。一个 Provider 可以同时挂在 `TRANSLATE` 与 `CHAT` 下，但配置实体必须按 capability 拆开：

```text
(user_id, capability, provider_id, model, priority)
```

失败只在同一 capability 内降级，不允许“翻译失败后偷偷切到聊天模型”而不标注。前端显示当前 Provider、降级原因和 `AI 生成` 标记；缓存命中不触发外部调用。

发音评分协议各家不同，单独实现 `AzureSpeechProvider`（音素级）/ `XunfeiProvider`（中文用户友好）/ `WhisperDiffProvider`（自建兜底：Whisper 转录后与目标文本做编辑距离，**只有文本准确度，无音素/韵律分**，返回时必须标注 `scoreDimensions` 缺失）。

以下接口是上述路由规则在代码中的唯一入口；业务模块不得直接注入或调用具体 Provider。选 provider 的输入仍是：**`capability` + 用户 region + 用户配置（`ai_provider_config`）+ `priority`**；系统预置 provider 与用户自配 provider 进同一个候选链（用户自配优先），逐个尝试，失败（超时/限流/额度耗尽/5xx）自动降级到下一个。

```java
public interface AiProvider {
    String id();                                   // "tencent-tmt", "libretranslate", "deepseek"
    Set<Capability> capabilities();
    boolean isSystemProvided();                    // true = 部署者配置，不属于任何用户
    boolean supports(Capability c, String model);
    <R> R invoke(AiRequest<R> request);            // 统一入口
    ProviderHealth health();                       // 熔断状态
}
public interface AiRouter {
    <R> AiResponse<R> route(Long userId, Capability capability, AiRequest<R> req);
}
```

| | |
|---|---|
| **理由** | 让用户"先去申请个 key"是最有效的劝退方式，所以机翻必须系统预置；而 LLM 单价高、用量不可控，必须 BYOK 把成本转移出去——两层的经济模型不同，配置模型就不能相同。**地区适配是内建需求不是可选项**：Google 翻译在国内基本不可用（`translate.google.cn` 已停），若只做一条链，一半用户第一次打开就看不到译文。OpenAI 兼容协议让新增一家国产模型的成本 = 加一行配置 |
| **代价** | 两套配置路径（系统级环境变量 + 用户级加密表）意味着两套测试和两套故障排查入口；机翻额度计数是一份需要维护的状态（跨月重置、并发累加、与账单对账都可能出错）；多一个 LibreTranslate 容器（约 1~2GB 内存）；抽象层用不到某家独有特性（prompt caching、structured outputs），需要 `extraParams` 逃生口；加解密带来密钥轮换负担（`key_version` 列支持双密钥并存） |
| **替代方案** | ① 全部 BYOK → 破产品红线，新用户零内容可看；② 全部系统预置（含 LLM）→ 我付 token 钱，个人项目烧不起；③ 只对接一家机翻 → 额度耗尽或地区不可用时功能整体消失；④ 不自建兜底，链尾放某家免费额度 → 额度是别人的，红线握在别人手里；⑤ Key 明文存库 → 一次注入或库泄露即全量泄露 |

### 5.4 词典查询走本地不走 AI

**决策**：ECDICT 770 万词条（含 `word/phonetic/definition/translation/exchange/tag/bnc/frq/collins/oxford`）全量落 `dict_entry`；Redis 缓存热词（`dict:w:{lemma}`，TTL 7 天，LRU）。目标 **P99 < 20ms**。AI 只做增值层：语境化释义、助记法、定制例句，结果按 `sha256(capability + model + normalizedInput)` 缓存到 `ai_cache` 表，Redis 做二级热缓存。

| | |
|---|---|
| **理由** | 查词是最高频操作（一集美剧划词几十次），AI 单次 300ms~3s 且要花钱，体验和成本双输；基础释义是确定性数据，本身不需要生成模型 |
| **代价** | 数据库多 ~1.5GB；导入脚本要处理编码和脏数据；ECDICT 释义质量参差（部分词条译文机翻痕迹重） |
| **替代方案** | ① 全走 AI → 慢且贵；② 走第三方词典 API → 有 QPS 限制、要联网、可能收费；③ 引入 Elasticsearch → 词典是精确/前缀查询为主，MySQL 主键 + 前缀索引 + `ngram` 全文索引已足够，ES 多一个要运维的 JVM 进程 |

### 5.5 词形还原用 ECDICT `exchange` 字段反查

**决策**：不用 Lucene stemmer / snowball。导入阶段解析 ECDICT 的 `exchange` 字段，构建正查表 `dict_form_index(surface_form → lemma, form_type)`。

```
exchange:  p:ran / d:run / i:running / 3:runs / s:runs
           ↑过去式 ↑过去分词 ↑现在分词  ↑三单    ↑复数
→ dict_form_index:  ran→run(PAST)  running→run(GERUND)  runs→run(THIRD_PERSON)

lemmatize(surface): ① 命中 dict_entry.word → 返回自身 ② 查 dict_form_index
                    ③ 都不中 → 规则去尾(-s/-ed/-ing) + 回查 dict_entry 验证
```

| | |
|---|---|
| **理由** | stemmer 是启发式截断，错误方向不可控：它会把 `running → run`（对），但 `better → better`（漏，实际应为 `good`）、`caring → care` 需要特例、`analysis → analysi`（错）。ECDICT 的 `exchange` 是人工/词库级数据，准确率高一个量级，且天然带 `form_type` 供前端展示"这是 run 的过去式" |
| **代价** | 依赖 ECDICT 的覆盖度，生僻词/新词的变形可能缺失（靠规则回退兜底）；`dict_form_index` 额外几百万行 + 一个索引 |
| **替代方案** | ① Lucene EnglishAnalyzer → 见上，精度不够；② spaCy/NLTK 微服务 → 引入 Python 进程，破坏单体部署；③ 调 AI 做还原 → 高频操作不能走 AI |

### 5.6 字幕以原文轨为唯一基准时间轴

**决策**：`subtitle_track` 只为**原文**建轨，译文作为 `subtitle_cue.translation` 字段存储，**不建独立的译文 track**。

```
官方英文:  [00:12.0─00:15.2] "I've been thinking about what you said."
官方中文:  [00:11.8─00:14.0] "我一直在想"  +  [00:14.0─00:15.5] "你说的那些话"
           ↑ 切分点不一致，硬按时间戳一对一匹配必然错位
```

两条归并路径：
- **AI 翻译路径**：逐 cue 送译，天然一对一，直接写 `translation`。
- **官方译文路径**：按时间区间做**重叠时长占比归并**——对每个原文 cue，取所有与之重叠的译文 cue，若某译文 cue 与该原文 cue 的 `overlap / duration(译文cue) > 50%`，则其文本拼入该原文 cue 的 `translation`（按开始时间排序拼接）。

| | |
|---|---|
| **理由** | 双轨模型下前端必须在每一帧做两次二分查找 + 对齐决策，且错位无法修正；单轨 + 字段让"当前句 → 译文"变成零成本的字段读取；逐句循环、收藏句、加入生词本的上下文快照都以原文 cue 为唯一 ID，语义清晰 |
| **代价** | 一句原文对多句译文时，译文会被拼接成一段（可读性略降）；换译文语言需要更新已有 cue 行而非新增一轨（用 `translation_lang` 列 + 覆盖策略解决，多语言场景需扩成 JSON 列） |
| **替代方案** | ① 双 track + 运行时对齐 → 前端复杂度高、错位难修；② 只显示原文 → 丢失核心功能；③ 全部重新 AI 翻译忽略官方译文 → 官方译文质量通常更好且免费 |

### 5.7 视频不下载，播放器用官方 iframe

**决策**：接入 YouTube IFrame Player API / Bilibili Player，**不下载、不转码、不代理视频流**。

```
Vue 页面
 ├─ iframe (YouTube / Bilibili)   ← 跨域：画面/原生字幕都拿不到；原生字幕 OFF
 │        ▲ seekTo()   │ getCurrentTime()
 └─ 自渲染字幕层 (iframe 外的普通 DOM)  ← 高亮 / 划词 / 生词着色
```

要点：关掉播放器原生字幕（`cc_load_policy=0`）；字幕层在 iframe **外**用普通 DOM 渲染，才能划词、绑定 hover、按生词本着色；用 `player.getCurrentTime()` 驱动高亮（`requestAnimationFrame` 轮询，见 §6.4）；`player.seekTo(t, true)` 实现逐句跳转与单句循环（循环 = 到达 `cue.end` 时 seek 回 `cue.start`）。

| | |
|---|---|
| **理由** | 版权风险归零；带宽和存储成本归零；播放稳定性和 CDN 由平台负责；不做转码就省掉 FFmpeg 依赖 |
| **代价** | 无法获取视频画面做截图/OCR；时间精度受 iframe API 限制（约 ±100~250ms，需要 §6.4 的容差处理）；平台改 API 或加防盗链会影响功能；离线不可用；某些视频有区域/嵌入限制 |
| **替代方案** | ① 下载 + 自建播放器 → 版权 + 存储 + 转码，全是坑；② 服务端代理流 → 带宽成本 + 明显违反平台 ToS；③ 只支持用户本地上传视频 → 内容供给不足（可作为补充能力，走 `StorageProvider`） |

### 5.8 异步任务用数据库状态机

**决策**：`async_job` 表（`job_type / payload / status / attempt / max_attempt / next_run_at / locked_by / locked_at / last_error / result_ref`）+ `@Scheduled` 轮询 + 悲观锁抢单 + 指数退避。

```
状态机:
  PENDING ──抢单──► RUNNING ──成功──► SUCCEEDED
     ▲                 │
     │                 └──失败 & attempt<max──► PENDING (next_run_at = now + 2^attempt * base)
     │                 │
     └──锁超时回收──────┴──失败 & attempt>=max──► FAILED (人工可重试)

抢单 SQL（悲观锁）:
  SELECT ... WHERE status='PENDING' AND next_run_at<=NOW(3)
  ORDER BY priority DESC, next_run_at LIMIT N FOR UPDATE SKIP LOCKED
  → UPDATE status='RUNNING', locked_by=:instanceId, locked_at=NOW(3)

僵尸回收: locked_at < NOW(3) - INTERVAL 10 MINUTE AND status='RUNNING' → 回 PENDING
```

`@Async` 线程池执行实际逻辑（虚拟线程 executor，IO 密集），轮询间隔 5s，每次最多抢 N 条。**适用场景**：ASR 转录、字幕批量翻译（一集 800 条 cue）、发音评分、文章解析与难度计算。

| | |
|---|---|
| **理由** | 单机部署、任务量小（个人使用日均几十到几百个 job）；任务状态需要**可查询、可重试、可展示进度**——数据库天然提供；`FOR UPDATE SKIP LOCKED` 让将来多实例也安全；MQ 在这个规模是纯粹的运维负担（多一个容器、消息丢失/重复要另建幂等表、状态查询还得再落库） |
| **代价** | 轮询有延迟（最坏 5s）；高频短任务下 DB 有额外压力；不具备 MQ 的扇出/优先级队列/延迟队列的成熟能力（优先级用 `priority` 列近似）|
| **替代方案** | ① RabbitMQ/Kafka → 过度设计；② Spring Events + `@Async`（纯内存）→ 重启丢任务、无法查询进度，不可接受；③ Quartz JobStore → 本质也是 DB 表，但表结构不为业务查询设计，还多一层框架 |

### 5.9 `tokens` 预分词结果落库

**决策**：`subtitle_cue.tokens` 与 `article_block.tokens` 用 MySQL JSON 列存预分词结果，导入/解析阶段一次性算好。

```json
[{"s":"I've","l":"have","b":0,"e":4,"p":"VERB"},
 {"s":"been","l":"be","b":5,"e":9,"p":"AUX"},
 {"s":"thinking","l":"think","b":10,"e":18,"p":"VERB"}]
```
（`s`=surface, `l`=lemma, `b`/`e`=字符偏移, `p`=词性；字段名缩写以压体积）

前端渲染只需：`tokens.filter(t => vocabLemmaSet.has(t.l))` → 一次 `Set` 求交即得需高亮的 token，O(n)。

| | |
|---|---|
| **理由** | 播放时每秒切句，若每次前端重分词，既要在浏览器里塞一份分词逻辑（还得和后端 lemma 规则保持一致），又要在每次切句时付 CPU；预分词把这个成本一次性前移到导入阶段。"已在生词本的词高亮"这个核心功能被降级为集合求交 |
| **代价** | 存储膨胀（约为原文的 3~4 倍）；分词规则升级需要重跑存量数据（用一个 `token_version` 列 + `async_job` 批量重算）；JSON 列不能有效索引 |
| **替代方案** | ① 前端实时分词 → 逻辑重复 + 每帧开销；② 单独建 `token` 表 → 一集视频几万行，读放大严重；③ 服务端每次请求现算 → 白白重复计算确定性结果 |
| **配套约定** | JSON 列**只做存储不做查询条件**（见 §9）。需要按 lemma 反查"哪些句子包含这个词"时，另建拍平的 `cue_lemma(cue_id, lemma)` 倒排表 |

### 5.10 打字拼写成绩直接映射 FSRS rating

**决策**：不为练习维护第二套熟练度进度，练习结果直接翻译成 FSRS 的四档 rating 写回 `review`。

| 打字表现 | FSRS rating | 判定条件（可配置阈值） |
|---|---|---|
| 一次打对且快 | **Easy** (4) | 零错字、零退格、零提示，且 `elapsed < 目标时长`（按词长 × 每字符 250ms 估算） |
| 打对但慢 / 有退格 | **Good** (3) | 最终正确，但有退格或超出目标时长 |
| 用了提示 | **Hard** (2) | 使用首字母/整词提示后完成 |
| 打错（放弃或超次数） | **Again** (1) | 未在允许次数内拼对 |

| | |
|---|---|
| **理由** | 与 §5.1 是同一条原则的延伸：不允许第二套进度。双进度体系必然发散（"打字满分但复习显示要背"），用户会不信任其中一个；FSRS 的 rating 语义本就是"回忆难易度"，打字流畅度是它的一个高质量代理信号；练习即复习，节省用户时间 |
| **代价** | 打字快 ≠ 真懂词义（可能只是肌肉记忆），存在评分噪声；键盘熟练度差异会系统性偏移 rating（可用用户基线打字速度归一化缓解）；阈值需要调参 |
| **替代方案** | ① 独立练习进度 → 双系统发散；② 练习完额外弹窗让用户自评 rating → 打断节奏，且自评噪声更大；③ 练习不参与调度 → 浪费了最强的信号源 |

### 6.2 Pinia store 划分原则

| store | 生命周期 | 说明 |

| `auth` / `settings` / `vocabulary` / `aiConfig` | 全局常驻 | `vocabulary` 只存 `Set<string>` 的 lemma 集合（几千个词，内存可忽略），是所有高亮的唯一数据源；增删生词时局部更新 Set，不重新拉全量 |

### 6.3 API 层

**方案**：`springdoc-openapi` 导出 `openapi.json` → `openapi-typescript` 生成类型 → 手写薄封装层调用。理由：类型从后端 DTO 自动同步，改字段编译期就报错；但完全用生成的 client 会丢掉统一的 `Result` 解包、错误 toast、loading 管理，所以保留一层手写封装。

`api/http.ts` 的四项职责：① 请求拦截注入 `Authorization: Bearer <access>`；② 响应拦截 `Result<T>` → `T`，`code != 0` 抛 `BizError`（携带 code 供上层判断）；③ 401 用 refresh token 换新 access，并把并发失败请求排队重放（单飞锁，避免并发刷新）；④ 网络错误/超时统一 toast + 上报。

### 6.4 播放器同步实现要点

**`requestAnimationFrame` 而非 `setInterval`**：rAF 跟随屏幕刷新（60fps），页面切到后台自动暂停（省电、避免后台空转），且不会像 `setInterval` 那样累积漂移；播放暂停时取消 rAF。**避免每帧 re-render** 的关键：`player.getCurrentTime()` 的返回值**不写入响应式 state**。

```ts
// usePlayerSync.ts 要点（伪代码）
let lastCueIdx = -1
function tick() {
  const t = player.getCurrentTime()
  const idx = binarySearchCue(cues, t)        // O(log n)，不进 reactive
  if (idx !== lastCueIdx) {                   // ← 只在“切句”时才触碰 DOM
    cueEls[lastCueIdx]?.classList.remove('active')
    cueEls[idx]?.classList.add('active')
    scrollIntoViewIfNeeded(cueEls[idx])
    playerStore.currentCueId = cues[idx].id   // 唯一写入响应式的地方，频率 ≈ 每句一次
    lastCueIdx = idx
  }
  if (loopMode && t >= loopEnd) player.seekTo(loopStart, true)
  raf = requestAnimationFrame(tick)
}
```

- **高亮用直接 DOM 操作**（`classList` 切换）或 `v-memo` 冻结不变的 cue 行；800 条 cue 的列表若每帧走 diff，即使有 `v-for` key 也会掉帧。
- 长字幕列表用虚拟滚动（仅渲染视窗 ±20 行），但"当前句"必须始终在渲染范围内。
- iframe API 时间精度约 ±100~250ms，切句判定加 ~80ms 容差，避免边界抖动来回切。
- 单句循环用 rAF 内的 `t >= loopEnd` 判定 + `seekTo`，不用 `setTimeout`（seek 会打乱定时）。
- 播放器状态用显式状态机（`IDLE / LOADING / PLAYING / PAUSED / SEEKING / ENDED`），避免 seek 期间的 `getCurrentTime()` 抖动触发误判。

## 7. 安全

| 项 | 措施 |
|---|---|
| **双 Token** | access JWT 有效期 15min，仅放在内存/`Authorization` 头（不入 `localStorage`）；refresh token 7 天，随机不透明串，**存 Redis**（`refresh:{userId}:{jti}`），可主动吊销；登出/改密码时删除该用户全部 refresh key。access 的黑名单也用 Redis（`jwt:bl:{jti}`，TTL = 剩余有效期），用于强制下线 |
| **刷新防重放 / 密码** | refresh 一次性使用（rotate）：换新 access 时同时签发新 refresh 并删旧的；旧 refresh 被重复使用 → 判定泄露，吊销该用户全部会话。密码 BCrypt（cost 12），永不记录明文/密文到日志；登录失败按 IP + 账号双维度计数，超阈值加验证码/锁定 |
| **API Key** | AES-GCM 加密（随机 IV + 认证标签），主密钥来自环境变量 `LEXIFLOW_MASTER_KEY`；`key_version` 列支持轮换；返回前端一律掩码 `sk-***abcd`；日志脱敏过滤器对 `sk-`/`api_key`/`Authorization` 做正则打码 |
| **上传校验** | 白名单 MIME + **magic number 实际探测**（不信 `Content-Type` 和扩展名）；音频 ≤ 10MB、字幕 ≤ 2MB、封面 ≤ 5MB；文件名重命名为 `{uuid}.{ext}` 落盘，禁止路径拼接（防目录穿越）；上传目录不可执行 |
| **录音保留期** | 默认 **30 天**自动清理：`async_job` 里注册每日定时清理任务，删除存储文件 + 置空 DB 引用；发音评分结果（分数/音素）保留，音频删除；用户可在设置里改保留期或手动立即删除 |
| **AI 限流** | Redis 令牌桶，维度 `user + capability`（如 CHAT 30 次/分钟、ASR 10 次/分钟、TTS 60 次/分钟）；另加每日 token 预算上限（读 `ai_usage_log` 当日累计），超限返回明确错误码而非静默失败 |
| **防 SSRF** | 文章 URL 导入与字幕抓取都会发出网请求，必须过 `SafeUrlValidator`：① 仅允许 `http/https`；② DNS 解析后校验 IP，**黑名单**回环（127/8、`::1`）、私有网段（10/8、172.16/12、192.168/16、`fc00::/7`）、链路本地（169.254/16 含云元数据 `169.254.169.254`）、`0.0.0.0/8`；③ 禁止跟随重定向到黑名单地址（**每一跳都重新校验**，最多 3 跳）；④ 独立 HTTP client，5s 超时、响应体上限 5MB、不带任何内部凭证；⑤ 端口白名单 80/443 |
| **其他** | CORS 白名单（不用 `*`）；`X-Content-Type-Options`/`X-Frame-Options`/CSP 响应头；所有写接口需 JWT；越权防护——每个查询都带 `user_id` 条件（不靠前端传 id 决定归属）；MyBatis 全部用 `#{}` 参数绑定，动态排序字段走白名单枚举 |

## 9. MySQL 使用规约

建表语句在 `04-database.md`，本节只定规约，DDL 文档必须遵守。

| 规约 | 说明 | 理由 |
|---|---|---|
| **主键** | 统一 `id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`，**不用 UUID** | InnoDB 是聚簇索引，随机 UUID 主键导致页分裂和写放大，且二级索引都要带上 16 字节主键，索引体积暴涨。需要对外隐藏 id 时另加 `public_id CHAR(22)`（Base62）列 |
| **时间** | 统一 `DATETIME(3)`，**存 UTC**，不用 `TIMESTAMP` | `TIMESTAMP` 有 2038 上限，且会按 `time_zone` 做隐式转换——同一条数据在不同连接时区下读出不同值，排查极痛苦。`DATETIME(3)` 到毫秒，够 FSRS 调度和 cue 时间使用。所有表带 `created_at` / `updated_at`；应用层用 `Instant`，只在展示层转用户时区 |
| **枚举** | `VARCHAR(20)` + 应用层 Java enum，**不用 MySQL ENUM** | MySQL ENUM 加值要 `ALTER TABLE`（大表锁风险），值的顺序还影响排序语义；`VARCHAR` + 应用层校验更灵活，也便于数据迁移。约定全大写下划线（`PENDING`、`THIRD_PERSON`） |
| **字符集** | 表与列必须 `utf8mb4` / `utf8mb4_0900_ai_ci`，连接串带 `characterEncoding=utf8mb4` | 字幕和用户笔记含 emoji 与生僻字，三字节 `utf8` 遇到四字节字符直接报错或截断。`_0900_ai_ci` 大小写与重音不敏感，正好匹配词典查询语义 |
| **JSON 列** | **只做存储不做查询条件**。需要过滤/排序的字段必须拍平成独立列 | JSON 上的索引（生成列 + 函数索引）维护成本高、优化器行为不稳定。`tokens`、`fsrs_param`、`ai_request_snapshot` 属于"整体读写"数据，适合 JSON；`status`、`lemma`、`due_at` 这类必须是真列 |
| **外键** | **不建物理外键约束**，由应用层保证引用完整性；但必须在文档中写清**逻辑外键**关系 | 物理外键在批量导入（ECDICT 770 万行）时严重拖慢写入、级联删除行为难控、且阻碍将来按模块拆库和数据迁移。代价是可能出现孤儿行，靠：① service 层校验 ② 逻辑删除优先于物理删除 ③ 定期一致性巡检 job 兜底 |
| **索引** | 每张表列出预期查询模式再定索引；遵守最左前缀；`user_id` 几乎总是复合索引第一列（多租户过滤）；避免超过 5 个二级索引 | — |
| **全文检索** | 需要中文/英文全文搜索时用 `FULLTEXT ... WITH PARSER ngram`（中文）或默认解析器（英文），`ngram_token_size=2`。**不引入 Elasticsearch** | 数据量级（百万行、单用户查询）远未到 ES 的收益区，省一个 JVM 进程的运维 |
| **软删除** | 用户可见数据用 `deleted_at DATETIME(3) NULL`（MyBatis-Plus 逻辑删除）；日志类表（`review_log`/`ai_usage_log`/`practice_attempt`）**只追加不删除**，按时间分区/归档 | — |
| **命名** | 表名单数小写下划线（`user_word`）；布尔列 `is_xxx TINYINT(1)`；金额/耗时带单位后缀（`latency_ms`、`est_cost_usd`）；不用 MySQL 保留字 | — |

## 11. 演进预留

| 场景 | 现在的准备 | 触发条件 |
|---|---|---|
| 拆出 `ai` 服务 | `ai` 模块零业务依赖、接口即 API 边界、无跨模块 JOIN | AI 调用量大到需要独立扩容或独立限流 |
| 拆出 `dictionary` 服务 | 叶子模块、只读、数据独立、可整体做只读副本 | 词典 QPS 或数据量成为单库瓶颈 |
| 引入消息队列 | `async_job` 的 `job_type + payload` 结构与 MQ 消息同构，执行器接口不变 | 单机轮询延迟不可接受，或需要多实例扇出 |
| 引入 Elasticsearch | 检索逻辑收敛在各模块 service 的单个方法内，可整体替换 | FULLTEXT 无法满足相关性排序或多字段打分需求 |
| 多实例部署 | JWT 无状态、抢单用 `SKIP LOCKED`、缓存在 Redis、文件走 `StorageProvider` | 单机资源不足（本项目预期长期不会触发） |
