# LexiFlow 开发路线图

> **TL;DR 1** — 分期标准从"技术栈是否完整"改成"作者自己是否愿意天天用"，S1 直接把 FSRS 间隔重复做进去，不做无算法的单词 CRUD。
> **TL;DR 2** — 视频精听从原 Stage7 提到 S2 作为主打功能，它同时是获客点、语料来源和复习时的语境回放来源，是整个产品的入口。
> **TL;DR 3** — Elasticsearch 和 RabbitMQ 砍掉，Redis 提前到 S1，MinIO 延后到 S5，日语横向扩展延后但数据库现在就预留 `language` 字段。

---

## 1. 设计原则

### 1.1 原 roadmap 的三个问题

原 roadmap 是**按技术栈分期**的：Stage1 无 AI 的 CRUD → Stage2 接 AI → Stage3 阅读 → Stage7 语音。纸面上整齐，落地会死。

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **Stage1 交付物不可用** | Stage1 做完是登录 + 单词 CRUD + 打卡 + 统计，作者自己都不会用它背单词，因为**缺间隔重复算法**。一个背单词产品没有 SRS，等于一个带登录功能的 Excel。 |
| 2 | **功能之间没有闭环** | 单词、阅读、听力、AI 是四个平行的 CRUD 模块，不是一条链。查到的词不会回到复习队列，复习时看不到当初查它的语境，听力练习不产生词表。 |
| 3 | **视频字幕排得太晚** | 视频字幕在原 Stage7。但它同时是获客点（别人一看就懂）、语料来源（字幕就是句库）、复习时的语境回放来源（点开单词跳回那一秒的画面）。这是产品入口，不是收尾功能。 |

### 1.2 新的分期原则

1. **每个阶段结束必须得到一个"作者自己愿意天天用"的东西**，而不是一个"技术上完整"的模块。阶段验收看使用意愿，不看代码覆盖率。
2. **单个阶段内允许技术不完整**。S1 的字典查询可以没有模糊搜索，但必须有 FSRS。缺功能可以补，缺核心算法整个阶段白做。
3. **每个阶段必须消费前一阶段的产出**。S2 的点词入库喂给 S1 的复习队列，S3 的语境化释义消费 S2 的语境快照，S5 的听打消费 S2 的字幕 cue。不允许出现孤岛模块。
4. **工程化不占用独立阶段**。Docker、CI、监控全程渗透，随每个阶段增量补，不攒到最后做一次"上线专项"。
5. **数据模型为延后功能留字段，代码不为延后功能留抽象**。`language` 字段现在就加，多语言的分词器抽象等真做日语时再写。反例是过早抽象出六个 Provider 接口然后只有一个实现。

## 3. 阶段详情

### S1 — 可用的背单词器

**目标**：有一个能算出"明天该复习哪些词"的背单词工具，作者当天就能停用其他 App。

| 交付项 | 说明 |
|---|---|
| 用户体系 + JWT | 注册、登录、刷新 token、密码重置；单用户也要走完整链路 |
| ECDICT 词典导入 | 770 万行词典数据入库，含音标、释义、词频、考试标签 |
| 词典查询 API | 精确查询 + 前缀查询；Redis 缓存热词 |
| 词形还原 | inflected form → lemma（looked → look，better → good） |
| 生词本 | 添加、删除、标记熟练度、分组（标签） |
| **FSRS 复习调度** | 卡片状态机、difficulty/stability/retrievability 计算、每日队列生成 |
| Redis 词典缓存 | 查询结果缓存 + 每日队列缓存 |
| 打字拼写练习 | 听音/看释义拼写单词，结果作为 FSRS 的 rating 输入源 |
| 前端 | 登录页、查词页、生词本、复习页、打字练习页 |

**完成标准（可验证）**

| 条件 |
|---|
| 导入后 `word` 表行数 ≥ 700 万，随机抽 100 个词查询全部命中 |
| 单词精确查询 P95 < 30ms（缓存命中 < 5ms） |
| 输入 `running` 能返回 `run` 的词条 |
| 复习队列由 FSRS 算出：同一个词答"忘记"和答"简单"，下次到期日不同且符合 FSRS 公式 |
| 打字练习的对错能改变该词的下次复习时间 |
| 连续使用 7 天，每天队列非空且不重复推同一批词 |
| 数据库所有词表、用户学习表都有 `language` 字段，默认 `en` |

**技术要点**：MyBatis 批量插入 + `rewriteBatchedStatements=true`；JWT 无状态鉴权 + Redis 存 refresh token 黑名单；FSRS 算法自行实现（参考开源实现但要读懂公式）；词形还原用离线词形表（不引 NLP 库）；Redis 用 String + Hash，热词 TTL 7 天。

**依赖**：无。

**验收 demo**：「我今天复习了 30 个词，其中 12 个是打字拼写通过的，明天该复习哪些是算出来的不是拍的。」

### S2 — 视频精听（主打）

**目标**：看 YouTube 或 B站视频时能点任意单词入库，并且带走当时那句话作为语境。

| 交付项 | 说明 |
|---|---|
| 视频源接入 | YouTube（IFrame Player API）、Bilibili、本地视频文件上传 |
| 字幕解析 | VTT / SRT / ASS 三种格式解析成统一 cue 结构 |
| 双语字幕对齐 | 中英字幕按时间轴匹配，容错处理条数不一致 |
| 播放器同步 | 字幕高亮跟随播放进度；点字幕跳转到对应时间点 |
| 点词查词入库 | 点击字幕中的词 → 查词卡 → 一键入库，带**语境快照**（句子原文 + 视频 ID + 时间戳） |
| 单句循环 | A-B 循环当前 cue，可设循环次数与间隔 |
| 字幕三档显隐 | 全隐藏 / 只显英文 / 中英双语，快捷键切换 |
| 视频难度标签 + 视频库 | 基于字幕词频分布估算 CEFR 等级打标签；收藏、观看进度、按难度筛选 |

**完成标准（可验证）**

| 条件 |
|---|
| 粘贴一个 YouTube 链接，10 秒内出现可播放视频 + 双语字幕 |
| 字幕高亮与音频偏差 < 300ms（人耳不觉得错行） |
| 点字幕中的词入库后，去 S1 复习页能看到这个词，且展开能看到原句 |
| 复习该词时能点一下跳回视频对应时间点继续播 |
| 单句循环 5 次不漂移（不会越循环越偏） |
| 上传一个 SRT 和一个 ASS 文件都能正常解析出 cue |
| 视频难度标签与人工判断在 20 个样本上一致率 ≥ 70% |

**技术要点**：YouTube IFrame Player API 的 `onStateChange` + `requestAnimationFrame` 轮询当前时间（不用 `setInterval`）；播放状态用前端状态机管理（idle / loading / playing / paused / looping / seeking），避免布尔标志位互相打架；字幕对齐用时间区间重叠度 + 贪心匹配；ASS 解析要处理特效标签剥离；本地视频用 `<video>` + Object URL；语境快照存 JSON 列。

**依赖**：S1（词典查询、生词本、FSRS 入库）。

**验收 demo**：「我在看一个 12 分钟的英文播客，点了 8 个不认识的词，全部进了今天的复习队列；复习时点一下就跳回视频里说这个词的那一秒。」

### S3 — AI 增强层

**目标**：词和句子的解释是按当前语境生成的，不是词典里抄的。

| 交付项 | 说明 |
|---|---|
| Provider 抽象 | 统一的 LLM 调用接口，支持多家；模型能力声明（是否支持流式、上下文长度） |
| BYOK 配置 | 用户自填 API Key + Base URL + 模型名，加密存储，可测试连通性 |
| 语境化释义 | 传入单词 + 所在句子 + 视频/文章标题，生成"在这句话里它是什么意思" |
| 助记法 | 词根词缀拆解、谐音、联想图景，按词生成一次后长期缓存 |
| 长难句解析 | 主干识别、从句层级、成分标注、中文直译 + 意译 |
| **AI 语境串词生文（Story Mode 引擎）** | 将今日待复习 15~20 词经**语义聚类 + CEFR 难度过滤**，约束生成连贯短文（带精确字符偏移量 JSON） |
| 字幕批量翻译 | 整集字幕一次性翻译并缓存，避免逐句请求 |
| 流式输出 | SSE 推送，前端逐字渲染 |
| AI 结果缓存 | 按 (prompt 指纹 + 模型) 缓存；命中不计费 |
| 用量记录 | 每次调用记录 token 数、耗时、成本估算；日/月用量视图 |

**完成标准（可验证）**

| 条件 |
|---|
| 同一个词在两个不同句子里，返回的释义不同且都正确 |
| 换一个 Provider（改配置不改代码）功能全部照常 |
| 提交 15 个跨学科生词，AI 能够通过语义聚类分成合理叙事框架，生成故事包含全部 15 个词且词性正确 |
| API Key 在数据库里是密文，日志和错误堆栈里不出现明文 |
| 字幕批量翻译一集 400 条 cue，第二次打开该视频 0 次 AI 调用 |
| 流式输出首字节 < 2s，中断请求能正确取消上游连接 |
| 缓存命中率在正常使用一周后 ≥ 40% |
| AI 服务不可用时，前端降级到词典释义而不是报错白屏 |

**技术要点**：Spring AI 或自建 HTTP 客户端 + SPI（`ServiceLoader` 或 Spring 的 `@Conditional` 注册）；Key 用 AES-GCM 加密，主密钥走环境变量不入库不入 git；prompt 模板外置成资源文件便于迭代；缓存双层（Redis 热 + MySQL 冷）；批量翻译走 `async_job` 表 + `@Async` 执行；流式用 `SseEmitter`，注意超时与客户端断开清理；Story Mode 结合轻量 Embedding 做语义余弦距离分组。

**依赖**：S1（词条数据）、S2（语境快照与字幕数据）。

**验收 demo**：「同一个 `charge`，在视频里那句话是"充电"，在另一篇文章里是"指控"，系统各自解释对了，而且第二次点开不花钱；系统还能拿我今天错的 10 个词自动写出一段悬疑故事，我在故事里把它们全部复习了一遍。」

### S4 — 阅读 + 浏览器插件

**目标**：在任何网页上划词查词，读的文章难度是匹配过的。

| 交付项 | 说明 |
|---|---|
| 文章导入 | 粘贴文本、URL 抓取正文、PDF、TXT、MD 四种入口 |
| 阅读器 + 划词查词 | 分段渲染、阅读进度、生词高亮；选中文本 → 查词卡 → 入库带语境（句子 + 文章标题） |
| **Story Mode 专属阅读流** | 一键进入“今日生词定制短文”阅读模式，高亮目标词，读完自动为涉及词汇产生 FSRS 识记反馈 |
| 已知词库 | 标记"已认识"的词；已知词不再高亮、不进复习队列 |
| i+1 难度匹配 | 计算文章生词率，推荐生词率在 2%–5% 区间的素材 |
| 素材推荐 | 基于已知词库 + 兴趣标签排序候选文章/视频 |
| Chrome 插件 | 任意网页划词查词入库，复用 S1/S3 全部 API；不重写业务逻辑 |
| 插件配置页 | 登录态、快捷键、高亮开关、生词自动标注 |

**完成标准（可验证）**

| 条件 |
|---|
| 四种导入方式各成功导入一篇，PDF 正文提取无乱码无页眉页脚残留 |
| URL 抓取在 10 个主流英文站点上正文提取成功率 ≥ 8/10 |
| 划词入库的词出现在 S1 复习队列，展开能看到文章原句 |
| 标记 300 个已知词后，同一篇文章的生词高亮数明显下降 |
| 推荐列表里随机 10 篇，人工判断"难度合适"≥ 7 篇 |
| 插件在 3 个不同网站（新闻/博客/文档站）划词都能弹卡并入库 |
| 插件不引入独立后端逻辑：所有请求打到主服务已有接口 |

**技术要点**：正文提取用 Readability 类算法；PDF 用 PDFBox 提文本 + 简单版面过滤；MySQL 8 FULLTEXT + ngram 做文章检索（不上 ES）；生词率计算需要已知词库 + 词形还原（复用 S1）；插件用 Manifest V3，content script 注入 Shadow DOM 避免样式污染；跨域走后端代理；插件 token 存 `chrome.storage.local`。

**依赖**：S1（词典、生词本、词形还原）、S3（语境化释义）。S4 的插件可以与 S5 并行开发。

**验收 demo**：「我在 Hacker News 上读文章，划词直接入库；系统还给我推了 5 篇生词率 3% 左右的文章，读起来不用查词典也不至于全会。」

### S5 — 产出型练习闭环

**目标**：从"看懂"变成"能听写出来、能说出来"。

| 交付项 | 说明 |
|---|---|
| 句子听打 | 复用 S2 字幕 cue 作为题源；**词级 diff** 高亮漏词/错词/多词；错词自动进生词本，同一句可重做并记录正确率 |
| 影子跟读 | MediaRecorder 录音、与原声波形对比、可重听 |
| 发音评分 | 可插拔 provider 接口（先接一家云服务或本地方案，接口保持可换） |
| AI 出题 | 选择题、填空题、翻译题、阅读理解，题源来自已学词与已读文章 |
| 每日/每周总结 | 复习量、新词量、听打正确率、跟读时长、薄弱词清单 |
| 导出 | Anki apkg / CSV 导出生词本（含语境与音频链接） |
| 存储抽象 | `StorageProvider` 接口，本地磁盘实现；录音文件走此接口 |

**完成标准（可验证）**

| 条件 |
|---|
| 从任意已导入视频一键生成 20 句听打练习 |
| 词级 diff 能区分"漏词""拼错""词序错"三种情况并分别标色 |
| 听打错词自动出现在次日复习队列 |
| Chrome 与 Edge 上录音、回放、上传全链路通 |
| 录音文件有明确保留期策略（默认 30 天），用户可一键清空 |
| 换掉发音评分 provider 只改配置不改业务代码 |
| AI 出题 20 道，人工检查无答案错误、无题干歧义 ≥ 18 道 |
| 导出的 apkg 能在 Anki 桌面端正常打开，卡片含正反面与语境 |

**技术要点**：词级 diff 用 Myers/LCS，需处理大小写、缩写（it's/it is）、标点归一化；MediaRecorder 输出 webm/opus，后端按需转码；音频波形用 Web Audio API 的 `AnalyserNode`；`StorageProvider` 只暴露 put/get/delete/signedUrl 四个方法，后续换 MinIO 不改调用方；AI 出题要带 few-shot 样例 + JSON schema 约束输出格式；总结报表用定时任务预聚合，不实时算。

**依赖**：S2（字幕 cue、视频时间轴）、S3（AI 出题、Provider 抽象）。

**验收 demo**：「我听打了 20 句，系统告诉我漏的全是弱读的介词和 -ed 词尾；我跟读了 10 句，发音分最低的是 /θ/；这些都自动进了我的复习清单。」

### S6 — 画像与学习计划

**目标**：系统知道我词汇量多少、弱在哪、今天该干什么。

| 交付项 | 说明 |
|---|---|
| Learning Profile | 词汇量估算、CEFR 等级估算、薄弱点标签、兴趣标签 |
| 词汇量估算 | 分层抽样测试（按词频分段抽词）+ 已知词库校准 |
| 薄弱点识别 | 从复习失败记录、听打错词、发音低分、语法题错项聚合出标签 |
| AI 学习计划 | 输入目标（如"三个月后考六级"）+ 可投入时间，输出周计划与每日任务 |
| 自动难度调整 | 根据近 7 天正确率动态调整每日新词量、素材难度、听打句长 |
| 计划执行看板 | 任务完成度、偏离预警、计划重排 |

**完成标准（可验证）**

| 条件 |
|---|
| 词汇量估算与一次独立在线测试结果偏差 < 20% |
| 薄弱点标签能追溯到具体证据（点击标签看到导致它的错误记录） |
| 生成的周计划任务全部可点击直达对应功能页（不是纯文本建议） |
| 连续三天完成率 < 50% 时，第四天任务量自动下调 |
| 连续三天完成率 > 90% 时，难度或量自动上调 |
| Profile 各字段有更新时间戳，能看到词汇量增长曲线 |

**技术要点**：词汇量估算用分层抽样 + 极大似然估计，不用简单百分比外推；薄弱点聚合走定时任务，结果落表；难度调整用带滞回的阈值（避免每天来回震荡）；AI 生成计划要约束成结构化 JSON，任务项带 `type` + `targetId` 才能直达。

**依赖**：S1（复习数据）、S4（已知词库、阅读记录）、S5（听打与跟读数据）。**注意：S6 必须在 S5 之后**，因为能力分析要有真实的产出型数据才不是分析空表。

**验收 demo**：「系统说我词汇量约 6800、B2 偏上，弱在连读和虚拟语气；给我排了三周计划，每天点进去就是具体的视频和词表，不是一段建议。」

### S7 — AI Native

**目标**：有一个能查资料、能排计划、能开口对话的学习助手。

| 交付项 | 说明 |
|---|---|
| RAG 知识库 | 语法书、四六级/雅思真题与解析资料入库、切块、向量化 |
| 向量检索 + 语法问答 | pgvector 或 MySQL 8 向量方案（视届时可用性定），混合检索（向量 + FULLTEXT）；「虚拟语气怎么用」→ 引语法书原文回答并带出处 |
| Agent 排计划 | 自动读 Profile → 排计划 → 写入任务表 → 到点提醒，无需人工点按钮 |
| 工具调用 | Agent 可调用查词、查视频库、查复习统计、写计划等内部工具 |
| 实时语音对话 | 流式 ASR + LLM + TTS，可打断；对话内容可转成生词与句子练习 |
| 对话记忆 | 长期记忆（偏好、目标）与会话记忆分开存储 |

**完成标准（可验证）**

| 条件 |
|---|
| 语法问答 10 个问题，答案均能给出资料中的准确出处段落 |
| 检索召回：给 20 个查询，Top5 命中相关块 ≥ 16 |
| Agent 能在无人干预下完成"读画像 → 排下周计划 → 发提醒"整条链 |
| Agent 工具调用有审计日志，失败可重放 |
| 语音对话端到端延迟 < 1.5s，可中途打断 |
| 对话里出现的生词能一键批量入库带对话语境 |

**技术要点**：切块按语义段落而非固定字数，保留标题层级作为元数据；混合检索用 RRF 融合排序；Agent 用有限步数 + 工具白名单，禁止自由 SQL；语音链路优先用支持流式的服务商，本地方案作为备选；长期记忆定期由 LLM 压缩摘要，避免无限增长。

**依赖**：S3（Provider 抽象、缓存）、S6（Learning Profile 作为 Agent 的输入）。

**验收 demo**：「我问它虚拟语气，它引语法书原文回答；我没让它排计划，周日晚上它自己把下周计划排好并提醒我；我还能直接跟它口语对话，对话里的生词自动进了词库。」

## 6. 砍掉 / 延后

| 项 | 决定 | 理由 |
|---|---|---|
| **Elasticsearch** | **砍掉** | MySQL 8 的 FULLTEXT + ngram 分词器够用到十万级文档。本项目文章量长期在万级，上 ES 意味着多一套集群、多一份索引同步逻辑、多一个数据不一致来源，收益为零 |
| **RabbitMQ** | **砍掉** | ASR 转录、批量翻译这类异步任务用数据库任务表（`async_job`）+ `@Scheduled` 轮询 + `@Async` 就够。任务表还自带持久化、可查询状态、可手工重试三个 MQ 要额外搭的能力。等真有并发压力再上 |
| **Redis** | **提前到 S1** | 词典查询缓存是刚需不是优化项。770 万行词表 + 每次复习翻十几个词，没缓存 P95 会难看。原计划放 Stage8 是把刚需当成锦上添花 |
| **原 Stage5 写作/口语能力分析** | **延后到 S6** | 系统里还没有写作和口语功能时，分析的是空数据。能力分析应该是功能的副产品，不是独立模块 —— 先有 S5 的听打和跟读，S6 的分析才有输入 |
| **日语支持** | **延后到 S9，但数据库现在就预留 `language` 字段** | 字段现在加是一行 DDL，S7 再加是全表 + 全接口 + 全缓存 key 的重构级别的痛。代码层的分词器抽象不提前做（只有一个实现的接口是负债） |
| **App / 小程序** | **延后到 S9 之后** | 浏览器插件性价比高得多：一份代码、无审核、能覆盖用户真实的阅读场景（网页），且完全复用现有 API。移动端要重写 UI、过审、处理离线同步，成本是插件的数倍 |
| **MinIO** | **延后到 S5** | S5 之前没有大文件需求。S5 用本地磁盘 + `StorageProvider` 接口抽象，跟读录音真上线且量起来时再换实现，调用方零改动 |
| **微服务拆分**、**多用户运营功能**（排行榜、社交、打卡分享） | **砍掉 / 不排期** | 单人项目，单体 + 模块化包结构足够，拆服务只会把方法调用变成网络调用；作者自己用不到的社交功能不进路线图 |

## 7. 风险清单

| 阶段 | 风险 | 表现 | 应对 |
|---|---|---|---|
| S1 | **ECDICT 770 万行导入性能** | 单条 insert 要跑几小时甚至 OOM | `LOAD DATA INFILE` 或 MyBatis 批量（batch 1000 + `rewriteBatchedStatements`）；导入时先删索引后重建；导入脚本可断点续传 |
| S1 | **FSRS 参数优化需要足够复习数据才有意义** | 上线就做参数拟合，样本几十条，拟合出来的参数比默认值更差 | 先用官方默认参数跑满 1000+ 次复习记录再谈优化；参数版本化存储，可回滚；优化开关默认关 |
| S2 | **YouTube 字幕接口不稳定 / 需要代理** | 接口改版、限流、国内直连不通 | 字幕获取抽成接口，多路径兜底（官方字幕 → 第三方 → 用户手动上传 SRT）；服务端可配代理；字幕一旦拿到就落库，不重复请求 |
| S2 | **双语字幕时间轴对齐错位** | 中英条数不等、一句英文对两句中文，播到后半段整体串行 | 用时间区间重叠度而非序号匹配；重叠度低于阈值时标记"对齐可疑"并允许手动微调偏移量；提供全局 offset 调节 |
| S2 | 播放器状态机竞态 | 循环 + 拖动 + 暂停组合操作导致播放跳飞或字幕卡住 | 显式状态机，禁止布尔标志位堆叠；所有 seek 操作串行化；写针对状态迁移的前端测试 |
| S3 | **BYOK 的 API Key 加密存储** | 明文入库、明文进日志、明文进异常堆栈、明文返回给前端 | AES-GCM 加密，主密钥走环境变量；DTO 层永久脱敏（只回显后四位）；日志脱敏过滤器；配置类禁止 `toString` 打印 Key |
| S3 | AI 成本失控 | 批量翻译一集就烧掉几美元，用户不知情 | 调用前预估 token 并提示；日/月用量上限可配；缓存优先；批量任务可暂停 |
| S4 | Chrome 插件样式冲突 | 划词卡在某些网站被网页 CSS 打乱或被 z-index 覆盖 | Shadow DOM 隔离；样式全部作用域内声明；在 10 个差异较大的站点上实测 |
| S5 | **MediaRecorder 浏览器兼容与录音隐私保留期** | Safari 支持格式不同、iOS 限制多；录音是敏感数据，长期堆在磁盘上是隐患 | 明确只承诺 Chrome/Edge 桌面端；格式协商（`isTypeSupported`）；录音默认保留 30 天自动清理，提供一键清空 + 明确的隐私说明；录音不进备份或备份单独加密 |
| S5 | 词级 diff 判定过严 | 缩写、大小写、标点差异被判错，用户觉得系统傻 | 归一化流水线（小写、去标点、缩写展开、数字统一）；diff 结果分"实质错误"与"格式差异"两级 |
| S6 | 词汇量估算不准 | 抽样偏差导致估算飘几千 | 分层抽样（按词频段）+ 足够样本量（≥ 100 词）+ 与已知词库交叉校准；给出置信区间而不是单一数字 |
| S7 | RAG 检索质量与版权 | 切块不当导致答非所问；教材资料版权风险 | 语义切块 + 混合检索 + 出处强制引用；只导入个人合法持有的资料，不做分发，明确标注仅本地使用 |
| 全程 | **单人业余时间估算偏乐观** | 每个阶段实际是估算的 1.5–2 倍 | 每阶段结束复盘实际人日并校准后续估算；阶段内按"能演示"切最小可用集，宁可砍功能不拖阶段 |
